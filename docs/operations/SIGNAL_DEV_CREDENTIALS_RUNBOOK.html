Credenciales de Signal Dev

Guía para conectar Oracle Dev, Risk Dev y Nexus Dev a signal-dev.opnconsultoria.com sin reutilizar credenciales de producción.

Regla esencial. Cada aplicación y cada entorno tiene su propia API key. No se comparte una clave entre Oracle, Risk y Nexus, ni se copia una clave de producción a desarrollo.

1. Qué hay que crear

Signal Dev es una instancia independiente: puede usar los mismos slugs de producto que producción porque su base de datos y sus claves son distintas. Los slugs no llevan el sufijo -dev; Signal los usa para aplicar el catálogo y las políticas correctas de cada producto.

Aplicación destinoNombre visible en Signal DevSlug exactoEstado actual
Oracle DevOPN Oracle Devopn-oracleDesplegado: configurar ahora.
Risk DevOPN Risk Advisor Devopn-risk-advisorServidor preparado, aplicación pendiente.
Nexus DevOPN Nexus Devopn-nexusEsperar: repositorio/despliegue aún no disponibles.

Por tanto, hoy solo es necesario materializar la clave de Oracle Dev. Las de Risk y Nexus se generan cuando sus aplicaciones estén listas para recibirlas; así no quedan secretos sin uso en el servidor.

2. Generar o rotar la clave en Signal Dev

  1. Abre https://signal-dev.opnconsultoria.com/admin/login e inicia sesión como administrador de Signal Dev.
  2. Ve a Consumidores API / Integraciones.
  3. Busca primero el slug correspondiente. Si ya existe, comprueba que es el consumidor de desarrollo y usa Rotar API key. Si no existe, pulsa Crear consumidor API.
  4. Al crear, rellena nombre y slug según la tabla anterior. Para Oracle, deja el webhook vacío por ahora, puntuación mínima 0 y límite inicial 120 peticiones/minuto.
  5. Guarda la clave que Signal muestra una sola vez directamente en el fichero secreto del servidor destino. Signal solo conserva su hash; después no se puede volver a consultar el valor original.
Si existe un consumidor con el slug correcto: no crees otro ni cambies el slug. Una rotación invalida de inmediato la clave anterior, por lo que hay que instalar la nueva antes de reiniciar la aplicación cliente.

3. Instalar la clave de Oracle Dev

Conéctate al servidor de desarrollo y crea el fichero solo si no existe. El servicio de Oracle se ejecuta como el usuario opn-oracle.

sudo install -d -o opn-oracle -g opn-oracle -m 0700 /etc/opn-oracle-dev/secrets
sudo install -o opn-oracle -g opn-oracle -m 0600 /dev/null \
  /etc/opn-oracle-dev/secrets/oracle_signal_ai_api_key
sudoedit /etc/opn-oracle-dev/secrets/oracle_signal_ai_api_key

En el editor, pega únicamente la clave nueva, guarda y cierra. No la añadas al historial del shell, a GitHub, a un ticket o a un chat.

Edita después /etc/opn-oracle-dev/oracle.env y añade o actualiza estas líneas:

SIGNAL_AI_BASE_URL=https://signal-dev.opnconsultoria.com
SIGNAL_AI_ALLOWED_HOSTS=signal-dev.opnconsultoria.com
SIGNAL_AI_API_KEY_FILE=/etc/opn-oracle-dev/secrets/oracle_signal_ai_api_key

Para habilitar búsquedas de licitaciones y fichas de entidad no hace falta habilitar modelos de IA. Mantén estas líneas como están:

AI_ENABLED=false
AI_MODE=disabled

Este ajuste conecta las consultas servidor a servidor de Oracle con Signal Dev; no requiere cambios de CORS ni de Nginx.

4. Aplicar y verificar Oracle Dev

sudo systemctl restart opn-oracle-api opn-oracle-worker opn-oracle-beat
sudo systemctl --no-pager --full status opn-oracle-api opn-oracle-worker opn-oracle-beat
curl --fail --silent --show-error https://oracle-dev.opnconsultoria.com/health/ready

Después, desde Oracle Dev, ejecuta una búsqueda de licitación pequeña o una consulta de entidad. El resultado esperado es una respuesta de Signal Dev sin errores de autenticación ni de host permitido.

Si falla, revisa exclusivamente mensajes redactados de los servicios; nunca imprimas el contenido del fichero secreto:

sudo journalctl -u opn-oracle-api -u opn-oracle-worker --since '10 minutes ago' --no-pager

5. Monitores y webhooks de Oracle (solo si se activan)

La configuración anterior cubre búsquedas y servicios gobernados de Signal. Los monitores de Signal Avanza son una integración adicional. No la actives hasta tener un token de Signal Dev y una conexión nueva desde Oracle Dev.

SIGNAL_AVANZA_ENABLED=true
SIGNAL_AVANZA_MODE=http
SIGNAL_AVANZA_CONTRACT_CONFIRMED=true
SIGNAL_AVANZA_ALLOWED_HOSTS=signal-dev.opnconsultoria.com
SIGNAL_AVANZA_BASE_URL=https://signal-dev.opnconsultoria.com/api/v1/oracle

Después crea la conexión desde la pantalla de integraciones de Oracle con esa URL y una credencial nueva de Signal Dev. No reutilices la conexión migrada de producción: sus secretos están cifrados con un keyring distinto y deben permanecer inutilizables en desarrollo.

6. Risk Dev y Nexus Dev

Cuando cada aplicación se despliegue, crea o rota su consumidor en Signal Dev siguiendo el mismo proceso y guárdalo como secreto local de esa aplicación.

AplicaciónVariables esperadasValor base
Risk DevSIGNAL_BASE_URL, SIGNAL_API_KEYhttps://signal-dev.opnconsultoria.com
Nexus DevLa configuración equivalente de su repositoriohttps://signal-dev.opnconsultoria.com

Risk y Nexus nunca usan la clave de Oracle. Si se habilita IA en cualquiera de ellos, aplica también en Signal Dev el preset/política del consumidor correspondiente antes de hacer pruebas funcionales.

7. Cierre

  • Se comprobó si ya existía el consumidor antes de crearlo.
  • La clave pertenece solo al entorno Dev y al consumidor correcto.
  • La clave vive en un fichero con permisos 0600, no en Git ni en texto compartido.
  • Oracle API, worker y beat se reiniciaron tras cambiar la configuración.
  • Se verificó una consulta real, limitada y no destructiva contra Signal Dev.
  • Producción no se modificó.
