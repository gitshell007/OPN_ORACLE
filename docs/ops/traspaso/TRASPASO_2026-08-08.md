### P0 · Oracle no tiene puerta remota en `oracle-dev`

El workflow completo solo corre en PR contra `master`. Todos los fallos de esta
sesión —mypy, limitador de peticiones, `raw_hash` duplicado, `tsc --noEmit`,
contrato divergente— se cazaron a mano porque no hay nada automático.

**Nota para quien escriba prompts:** `build-release.sh` ejecuta **cinco** puertas
y es fácil pedir solo tres:

```
npm run lint · npm run typecheck · npm run test -- --run
npm run api:client:check · npm run build
```

`typecheck` incluye los ficheros de test. Los de integración de la API exigen
`ORACLE_RUN_INTEGRATION=1` más `TEST_DATABASE_URL`, `TEST_RUNTIME_DATABASE_URL` y
`TEST_REDIS_URL`. **Su fixture hace `downgrade base` + `upgrade` + `flushdb`:
arrasa la base que se le indique.** Usar siempre una desechable.

### P1 · `ai_policy_denied` es demasiado grueso

Tres causas distintas comparten código, y la interfaz adivina mal:

```
política ausente o kill switch  →  ai_policy_denied
proveedor no autorizado         →  ai_policy_denied
modelo no autorizado            →  ai_policy_denied
```

Visto en vivo: con `allowed_models=["qwen3.5:9b"]` obsoleto, la pantalla decía
«La IA está desactivada, pídeselo a un administrador de plataforma» — falso por
partida doble. Separar en `ai_policy_disabled`, `ai_provider_not_allowed` y
`ai_model_not_allowed`.

### P1 · «Probar conexión» es un falso positivo

`test_connection` encola un evento y responde 202; el worker ejecuta un `health`
que **no atraviesa la puerta CMS**. Da «Saludable» aunque el tenant no esté
autorizado y todo lo real vaya a fallar. Debe ejercer algo que pase esa puerta.

### P1 · Signal: entrega del secreto fail-open

## 4. Lecciones de la sesión

**Los tests verdes de un solo lado no prueban una integración.** Oracle y Signal
implementaron `ORA-AUTOGRANT` y `SIG-AUTOGRANT` contra contratos distintos
—`/scopes/ensure` frente a `/dossiers/{id}/authorize`— y **ambos informaron verde**
porque cada uno probó contra su propio simulador. `/scopes/ensure` era un stub que
exigía la concesión en vez de crearla. Se detectó comparando los dos lados contra
el servidor, no leyendo los informes.

**Las cadenas literales del contrato hay que compararlas entre repos.** Que
`dossier_authorization_manual_required` coincida en ambos lados no lo garantiza
ningún test de ninguno de los dos.

**Un test puede consagrar el fallo.** El guardián de entorno cruzado empezaba con
`if app_env == "production": return False`, y oracle-dev corre con
`APP_ENV=production`: quedaba inerte justo donde importaba. El test **afirmaba**
ese comportamiento. Y el de recuperación de contraseña hacía login antes de
llamar a «he olvidado mi contraseña», escenario que no existe: la recuperación
llevaba rota desde el 28 de julio con `password_reset_tokens` a cero filas.

**El patrón recurrente de esta base de código es afirmar lo que no se ha hecho.**
Apareció seis veces en una sesión: respuestas que negaban datos existentes,
pantallas que decían «no configurado» sin poder comprobarlo, un 204 de «te hemos
enviado un correo» sin enviarlo, un `authorized: true` que no persistía nada, un
«Saludable» que no atraviesa la puerta, y un «La IA está desactivada» cuando el
problema era el modelo.
